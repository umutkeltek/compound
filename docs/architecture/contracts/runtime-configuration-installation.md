# Closed inactive runtime configuration installation

The v0.2 owner installs four semantic slots: app, API, migrator and web. The
first basename is `.env`; the other names, consumer keys, API field roster,
container names and web literals come from a frozen profile artifact. Public
source and fixtures contain no product-specific runtime identity.

`runtime.config_installation.exact` can only HOLD for a fresh one-use native
approval. Its metadata request binds the complete protected target, original
file custody, explicit companion absence, root directory identity, inactivity
marker and lock, SSH and executable pins, database/role identities, verifier
qualification, source capture qualification and frozen profile. Every matching
custom forbidden rule and independent denying floor remains effective. An
allowing class, grant or autonomy level cannot bypass exact approval.

## Native evidence and secret custody

The credential qualification must be an actual native verifier plan, succeeded
committed RunAttempt and matching owner Receipt/Transition/observation. A
standalone successful receipt is insufficient. The capture qualification must
be a completed native Work whose terminal proof binds the qualification
artifact and original source ActionIntent/PolicyDecision. That artifact pins
the original source attempt/result/public metadata, exact private file custody,
selected-field digest and frozen consumer profile. Its qualification Action
arguments bind the artifact excluding only its action/policy backreferences.

The owner opens the private capture through anchored no-follow descriptors,
checks stable file and ancestor identities, and extracts only
`services.api.record.selected`. The request and native artifacts carry metadata
only. Selected provider values travel in memory on bounded stdin. Database
credentials come only from the qualified target `.env`, parsed by the exact
embedded credential verifier. URL construction preserves each role's password
provenance; no caller can supply final DSNs or staged file contents.

## Filesystem transaction and uncertainty

The fixed Python dispatch performs real descriptor-anchored writes. It retains
the inactivity fence and lock, verifies the host/cluster/role/database state,
rejects relevant active sessions and containers, and checks all four file slots
before each publication. The original bytes, every staged payload and a
manifest are fsynced before target writes. Journal records use atomic no-replace
publication. Companion publication uses Linux libc `renameat2(RENAME_NOREPLACE)`
and has no overwrite fallback. Every rename is followed by source and target
directory fsync. Postimages are custody observations, never file contents.

Four renames are not atomic. A failed launch or lost response can leave partial
files. Native uncertainty uses `change_knowledge: unknown` and omits `changed`;
it does not claim zero effects. The original reservation retains its required
attempt completion and separate recovery obligation even after a failed native
owner Receipt/Transition is published. Persistence failure retains the blocker.

## Separately admitted recovery

`recovery-plan --plan-ref ORIGINAL --operation reconcile|rollback --work W`
requires the separate recovery Work named by the original reservation. It binds
the original action, attempt, request, failed proof and exact operation under
`runtime.config_recovery.exact`. A new one-use native approval is mandatory.
Recovery needs no private capture projection and cannot start a new install.

The same shipped dispatch opens retained transaction evidence and classifies
all four slots before any recovery write. Drift refuses recovery. Reconcile
can confirm an entirely published, fsynced inactive configuration; otherwise it
reports recovery required. Rollback restores the retained original and removes
only proven published companions, retaining evidence across interruption.
Repeated rollback recognizes its own restored inode. Unrelated root assets are
preserved. The recovery attempt carries its own native proof. The original
failed attempt remains failed; only a verified succeeded recovery chain can
release its blocker. Interrupted local finalization is completed before planning
remote recovery, without weakening the original reservation.

If a successful remote result was sealed but native owner-proof publication
failed, retrying the same execute plan resumes local finalization from that
immutable observation and receipt. It never starts transport or consumes another
approval. A descriptor-held process lock excludes concurrent execute retries and
recovery planning while the original owner is active; a crashed process releases
the lock without clearing its native reservation.

## Verification boundary

Synthetic Go tests exercise native qualification, exact approval, RunAttempt,
unknown receipt, reservation and separate recovery integration. Linux tests run
the actual dispatch, password parser and filesystem owner with a synthetic
external observer; they test process death at install/rollback boundaries,
fsync failures, short writes, no-replace behavior and custody drift. These are
implementation evidence, not live host installation or database acceptance.
The credential verifier's own actual PostgreSQL regression remains separate.
No configuration or application activation is authorized by source delivery.
