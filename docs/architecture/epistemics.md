# Epistemics Contract

Compound treats epistemic doctrine as an enforced contract, not ambient prose. The rows below are deliberately machine-parseable by `compound architecture doctor --strict`: each principle names the existing implementing object family and at least one CLI verb that proves the branch is observable.

| n | principle | implementing_object | proof_command |
|---|---|---|---|
| 1 | Expectations become explicit contracts before execution, so later agents can inspect included and excluded context instead of guessing. | internal/contract, internal/harness | compound contract compile |
| 2 | Work has one root identity from intent through receipt and transition; reports without a closed proof chain do not count as completion. | internal/work, internal/envelope | compound workbench |
| 3 | Determinism changes when evidence changes; contradiction evidence must reopen review instead of leaving stale promoted meaning ambient. | internal/mem | compound synthesis sweep |
| 4 | Capability selection is evidence-aware and auto-surfacing only; offers never execute without WorkEnvelope and policy proof. | internal/capgraph, internal/panel | compound capability surface |
| 5 | Routing is an epistemic choice as well as a cost choice; route evidence is never task success until joined to receipt state delta. | internal/routeevidence, internal/product | compound route outcome-review |
| 6 | History becomes evidence, evidence becomes adjudicated claims; stored does not mean true, and only promoted meaning enters ambient recall. | internal/knowledge, internal/distiller, internal/candidates | compound memory recall |
| 7 | Public core stays generic while external capability enters only through gated intake, review, and no-promotion evidence before activation. | internal/arch, internal/capgraph | compound architecture doctor |
| 8 | Suggested work is propose-only: the director emits capped, evidence-backed create-plan previews and run reports, while admission, execution, and owner mutation require operator provenance. | internal/director, internal/work | compound director propose |

**Suggested-work boundary.** The director organ (`internal/director`, driven only by `compound director propose`) is the system's highest drift risk — the place a suggestion engine could quietly grow into a scheduler or boss. Its boundary is therefore stated and enforced explicitly, not assumed. A director run: has **no background or scheduler mode** (a single synchronous `Propose()` call, no goroutines, timers, or process exec); performs **no auto-admit** (the `internal/work` auto-admit seam is inert — kill-switch-gated and with no shipped caller granting `EligibilityReason`); does **no auto-continue** and takes **no external side effects**; performs **no memory promotion** and **no policy edits**; caps output at **max 5 proposals per run**; **requires evidence refs** on every proposal; applies **duplicate suppression** against open work and prior proposals; and leaves each proposal at `State:"proposed"` so **operator review is required before advancement**. On `--apply` it writes only proposal surfaces — the create-plan previews, the run report under `projections/director/runs/`, and the enclosing run WorkEnvelope's own receipt/transition proof — never memory, policy, config, or source/product/review owners. User-facing surfaces say "suggested work"; "director" stays an internal package name, not a user-facing command persona. This invariant is guarded by `internal/director` boundary tests (write-surface confinement) and `cmd/compound` CLI-surface tests (propose is the only verb), in addition to the doctrine row above.

**Editable-surfaces boundary (EVOLVE-BLOCK).** The kill-switch answers "may the system admit ANY autonomous work now?"; a sibling **editable-surfaces registry** (`internal/policy/editable_surfaces.go`, live-loaded from `$COMPOUND_HOME/config/editable-surfaces.yaml`, surfaced by `compound policy editable-surfaces --json`) answers "for a system-originated proposal that declares a `target_surface`, is THAT surface one the operator has explicitly, actively opened for edits?". It is fail-closed: an absent, empty, or invalid registry makes **nothing** editable, and a compiled-in HARD-DENY core — `policy`, `permissions`, `ledger`, `evaluator` — can never be whitelisted (listing one is a loud validation error that invalidates the whole registry), so the evaluator and the policy/permission/ledger spine stay outside any loop that could edit them. Enforcement runs at the same admission seam the kill-switch guards (`internal/work` `AdmitAuto` + the generic `Advance` seam), AFTER the halt check so a halt always wins; a proposal without a `target_surface` is ordinary work and is unaffected. Guarded by `internal/policy` and `internal/work` falsifier tests (hard-deny core, absent/active/retired lifecycle, halt-wins).

Known open gaps stay packet-sized: expectation claims outside product loops belong to the EffectiveContract stage; directional generic/specific recall belongs to the directional graph packet; full scope lattice content belongs to the later scope-lattice work. These are not separate doctrine engines.
